# 自定义规则已保存，焦点为什么仍显示原文？

适用于 FocusRestore 0.54.2 / versionCode 364 的 OS3、OS4 状态栏焦点正文转换。先看实际加载的模块、当前通知和显示模式，再决定在哪一步复测。

0.48.2 是公开升级基线。内测版规则与授权留在原有私有位置。升级后可从最近记录重建，或者导入符合当前格式的规则包。共享 UID 设备使用新版授权清单。

## 先取得一条可复现的记录

1. 在「关于 → 自定义规则 → 开启最近记录」手动开始捕获，然后在目标应用触发一次实际焦点通知。捕获对本次会话全局生效，无需先选应用。普通通知和历史通知不会仅凭包名进入最近记录。
2. 回到「从最近记录新增或更新规则」，选择目标应用的记录。发现可编辑字段时，可跨组勾选最多 16 项并长按已选卡片拖动，大字为示例，小字为登记路径。核对预览后点底部「保存规则」。
3. 新建规则会保存捕获时的协议、业务、场景和完整可用字段集合；勾选只决定显示字段及顺序。比如捕获到 `/baseInfo/title`、`/desc1`、`/desc2` 的通知，新规则会在同包的相同类型和完整结构上生效。字段缺少或增加时可以为新的结构单独建规则。同一集合中的字段顺序变化不影响匹配。选择更新会保留规则的标识、位置和启停状态。
4. 使用严格身份读取的设备会直接核对 SystemUI 加载状态；平台共享 UID 使用单独确认的最小投影。批准当前清单时，核对应用、可用于区分通知的结构及显示字段顺序。删除或停用一条规则后，其余内容一致的已批准规则可以继续加载。新增、更新或启用后应重新确认。[授权内容与撤销](island-rule-projection.md)
5. 在「规则迁移」导入 `.frpk`。预览中可以对照本地与导入规则的字段顺序，逐条勾选要替换的重复规则。导入优先级变化可能影响横幅选用的规则。其他本地规则保留。导出默认清除示例文字，保留类型和字段顺序。收到脱敏包时，可按路径辨认字段。

## 按出现差异的位置定位

| 观察到什么 | 下一步要核对什么 |
|---|---|
| 导入结果显示已保存，状态栏仍是内置正文 | 在结果页点「完成」，按提示确认 SystemUI 读取当前规则。已关闭结果页时，可从「关于 → 自定义规则」打开同一读取确认。授权后用同类型的新通知核对快照与正文。 |
| 设置页已显示 0.54.2 | 在 Debug 抓取的同一时间段找当前 SystemUI 主进程的 `entry loaded`，核对版本 0.54.2、code 364、debug 标记和 PID，再对照设置中的 OS 模式。缺少加载行时，记录实际能确认的版本和 PID。覆盖安装和一次 App 点击只能证明各自发生过。 |
| 0.51.0 点击捕获记录后退出设置 | 0.51.1 修正列表从页面移除前的监听清理。若仍可复现，保留 App 进程 `com.hyperos3.focusrestore` 的 `AndroidRuntime` 异常栈；SystemUI 探针不覆盖 App 崩溃。 |
| 开启后没有最近记录 | 核对开关开启时间、屏幕及解锁状态、当前用户和桥连接，然后重新触发一条实际显示的目标焦点。无可编辑岛字段的焦点也会列出摘要和原因。最多保留 30 条，达到字节上限时可能提前淘汰较早记录。结束会话会清空记录。 |
| 预览正确，保存后仍显示旧顺序 | 在管理页定位具体规则，核对是新增还是更新、启停状态、优先级及声明顺序。App 仓库修订表示保存成功，再查 SystemUI 是否已载入对应清单。共享 UID 下尤其要核对授权所列包名和路径的顺序。 |
| 快照已加载，正文仍是内置文本 | 确认转换已开启且目标通知经过当前模式的转换准入。全文按优先级降序、同级声明先后尝试规则，首条生成非空正文者获胜。字段缺失、空结果、无匹配、解析失败、超时或任务失效时保留内置正文。原生优先、白名单和通知所有权仍影响准入。 |
| Debug 有 `MATCHED`，屏幕或读屏仍不一致 | 用同一通知、同一候选和同一代次核对最终可见正文与无障碍描述。全文应取这一候选的同一正文。切到“药丸左右拼接”（简略）时核对原两侧文字。对有计时的通知，再停用对应规则，核对内置计时恢复并持续更新。切候选、移除、更新 payload、换修订后都要重新确认，旧异步结果只能用于原代次。 |

Debug 中 `rule snapshot state=loaded` 可核对快照代次和启用条数，`rule body outcome=MATCHED` 可关联胜出的规则。无可用输出时查 `NO_MATCH_OR_INVALID`，超时查 `DEADLINE`，队列拒绝查 `REJECTED_QUEUE_FULL`。发生代次失效时，迟到结果可能被直接丢弃。保留观察到的阶段和固定原因码即可。收集日志的步骤见[项目日志说明](../README.md)。

遇到先显示所选字段、随后恢复整段文字时，保留同一 PID 和通知 key 的前后布局。先核对 `rule snapshot invalidated reason=`，再看 `rule snapshot read failed reason=`。`projection-notified` 表示读取端收到了投影变更通知。`RULE_PROJECTION_NO_PAYLOAD` 表示该次读取没有数据，可能涉及授权、并发读取或存储状态。此时在 App 核对本次修订的授权和就绪状态。保持规则不变，连续观察状态栏至少 60 秒，可覆盖多次 15 秒的定期核对。

## 怎样验收

在 OS3、OS4 分别记录模块加载行及复现时间、App 保存修订、SystemUI 快照状态、最终焦点正文、读屏描述和计时变化。用同一条通知分别核对全文与简略，再测试一次停用、一次换修订或撤销授权。可用记录滞后或取消时，以当时屏幕和读屏实际结果为准。JVM 覆盖规则计算和状态边界，设备负责确认最终可见与可读结果。

工作树接口见[规则格式](island-rules-spec.md)、[登记路径](island-rule-paths.md)与[最近记录及导出合同](capture-export-spec.md)。
